## 1. Executive decision

The immediate experiment will use:

- Four prompt versions: P0, P1, P2, and P3.
- Two feature families: F0 and F1.
- Three demonstration-retrieval methods: D0, D1, and D2.
- Two demonstration policies:
  - DP_LOW: 1 fraud + 1 non-fraud.
  - DP_HIGH: 10 fraud + 10 non-fraud.
- One fixed row representation: R0.
- One fixed model: Gemini 2.5 Pro.
- A fixed temperature of 0.1 unless the existing approved configuration says otherwise.
- A fixed seed of 2026.

This produces:

~~~text
4 prompts
x 2 feature sets
x 3 retrieval methods
x 2 demonstration policies
= 48 configurations
~~~

There are 24 F0 configurations and 24 F1 configurations.

The final selection variables remain:

~~~text
Y1 = best validated configuration whose feature family is F0
Y2 = best validated configuration whose feature family is F1
Final comparison = Y1 versus Y2 on the same untouched final targets
~~~

The two-policy design is an intentional deadline-driven reduction of the originally proposed five-policy grid. It can establish whether the low-context and high-context endpoints differ, but it cannot prove that an omitted intermediate demonstration count would not perform better. That limitation must be stated in the final presentation.

## 3. Sampling-fraction correction and provenance

The original training population is approximately 77.446 million debit-card transactions. The fraction needed to obtain approximately 77,000 rows is approximately:

~~~text
0.001 as a fraction = 0.1 percent
~~~

The value 0.0001 is 0.01 percent and would produce only approximately 7,745 rows from a 77.446 million-row population. Therefore:

- If the intended training fraction was 0.1 percent, the code should contain 0.001.
- If an artifact says 0.0001 while also reporting approximately 77,884 rows, flag the artifact as internally inconsistent.
- Record the observed fraction as observed_train_rows / source_train_rows.

The historical OOT construction was approximately:

~~~text
first stage: 5 percent of the original OOT population
second stage: 0.1 percent of the first-stage population
net fraction: 0.05 x 0.001 = 0.00005 = 0.005 percent
~~~

For an OOT source of approximately 24.7 million rows, that net fraction produces approximately 1.2K rows, which is consistent with the 1,206/1,236-sized frozen cohorts.

No experiment should resample from the original 24.7 million rows. Development cohorts must be selected from the already frozen final OOT manifest so the evaluation lineage remains explicit.

## 4. Exact experiment axes

### 4.1 Prompt axis

The prompt axis contains P0, P1, P2, and P3.

Each prompt must be stored as a versioned text artifact. The experiment runner must log:

- Prompt ID.
- Prompt-content hash.
- Prompt character count.
- Estimated or observed input-token count.
- Output-format instruction version.

Only prompt wording may differ across P0-P3. Feature values, target IDs, selected demonstrations, demonstration order, model settings, and parser must remain fixed for a paired prompt comparison.

### 4.2 Feature axis

F0 is the engineered feature family:

- Expected to contain 94 ordered features.
- Its manifest must define the exact feature order.
- The same F0 definition is used to describe the target and demonstrations.
- F0 retrieval preprocessing is fitted only on the frozen training-candidate pool.

F1 is the alternative/raw feature family:

- Expected to contain approximately 5-6 natural/raw features.
- Its final ordered manifest must be created and frozen before F1 nearest-neighbor retrieval runs.
- Each F1 column must have an explicit type: numeric, categorical, Boolean, or timestamp-derived.
- F1 retrieval preprocessing must be independently fitted on the frozen training-candidate pool.

Primary-grid rule:

~~~text
F0 configuration = F0 display data + F0 retrieval data
F1 configuration = F1 display data + F1 retrieval data
~~~

Do not include cross-feature hybrids such as F0 display with F1 retrieval in the primary grid. Such hybrids would be a separate experiment family.

### 4.3 Retrieval axis

D0, D1, and D2 determine which labeled historical transactions become demonstrations. They do not generate the fraud prediction.

- D0: deterministic label-stratified random control.
- D1: cosine nearest-neighbor demonstration retrieval.
- D2: Euclidean nearest-neighbor demonstration retrieval.

Gemini, not the retrieval method, produces the fraud-risk score.

These methods are nearest-neighbor ICL retrieval methods, not k-nearest-neighbor classifiers. Neighbor labels do not vote. Retrieved rows are inserted into Gemini's context.

### 4.4 Demonstration-policy axis

Only these two policies are active in the immediate reduced grid:

| Policy ID | Fraud demonstrations | Non-fraud demonstrations | Total |
|---|---:|---:|---:|
| DP_LOW_1F_1N | 1 | 1 | 2 |
| DP_HIGH_10F_10N | 10 | 10 | 20 |

Reasons for selecting the endpoints:

- They provide the strongest possible low-context versus high-context contrast.
- They measure whether a large context materially improves discrimination.
- They expose the token, latency, and reliability cost of 20 examples.
- They reduce the grid from 120 to 48 configurations.
- DP_LOW is a prefix of DP_HIGH when retrieval rankings are frozen, improving paired comparability.

Do not describe this reduced experiment as identifying the globally optimal number of demonstrations. It compares two prespecified endpoints.

## 5. Demonstration-selection contract

Every target receives fraud and non-fraud demonstrations separately.

### 5.1 D0 deterministic random control

D0 must support both demonstration policies. A single fixed 10F/10N block is not sufficient.

For each target and label:

1. Filter the frozen training pool to the requested label.
2. Produce a deterministic pseudo-random ordering using:
   - Target transaction ID.
   - Candidate transaction ID.
   - Seed 2026.
   - Candidate-pool version.
3. Break hash ties using candidate transaction ID.
4. Store at least the first 10 ordered candidates for each label.
5. DP_LOW uses rank 1 from each label.
6. DP_HIGH uses ranks 1-10 from each label.

This guarantees that the D0 low-policy demonstrations are contained in the D0 high-policy demonstrations.

### 5.2 D1 cosine retrieval

For each target:

1. Transform the target with the frozen feature-family preprocessing object.
2. Transform the fraud and non-fraud candidate pools with the same object.
3. L2-normalize the standardized vectors.
4. Calculate cosine similarity.
5. Rank candidates within each label from largest similarity to smallest.
6. Break exact ties using candidate transaction ID.
7. Persist the first 10 ranks per label.
8. Use rank 1 per label for DP_LOW and ranks 1-10 per label for DP_HIGH.

### 5.3 D2 Euclidean retrieval

For each target:

1. Use the same median-imputed, training-standardized feature space.
2. Do not apply the cosine-specific L2 normalization.
3. Calculate Euclidean distance.
4. Rank candidates within each label from smallest distance to largest.
5. Break exact ties using candidate transaction ID.
6. Persist the first 10 ranks per label.
7. Use rank 1 per label for DP_LOW and ranks 1-10 per label for DP_HIGH.

### 5.4 Demonstration order inside the prompt

Hold demonstration ordering constant:

~~~text
fraud rank 1
non-fraud rank 1
fraud rank 2
non-fraud rank 2
...
fraud rank 10
non-fraud rank 10
~~~

DP_LOW is therefore the first two records of DP_HIGH.

Do not randomly shuffle demonstration order by configuration. Prompt order is a possible confound and must be fixed.

### 5.5 Retrieval reuse

Retrieval must not be repeated for every prompt.

Precompute and persist rankings using this key:

~~~text
feature_set_version
target_transaction_id
retrieval_method
candidate_label
retrieval_rank
candidate_transaction_id
similarity_or_distance
retrieval_preprocessing_hash
candidate_pool_hash
~~~

P0-P3 and both demonstration policies must reuse the same persisted rankings. Retrieval scores should be stored for auditability but should not be shown to Gemini unless a separate experiment explicitly tests that behavior.

## 6. Retrieval preprocessing

Retrieval preprocessing and prompt display are related but separate representations.

### 6.1 Numeric retrieval columns

Fit all preprocessing statistics on the frozen training-candidate pool only:

1. Convert approved numeric features to numeric values.
2. Replace positive and negative infinity with missing.
3. Compute and freeze the training median for each feature.
4. Fill missing values with the frozen training median.
5. Compute and freeze the training mean and scale.
6. Standardize each value:

~~~text
z = (value - frozen_training_mean) / frozen_training_scale
~~~

7. If a feature has zero scale, replace the divisor with 1 and log the feature.
8. Store the ordered feature list and preprocessing statistics.
9. Hash the complete preprocessing artifact.

Never fit imputation or scaling on the OOT targets.

### 6.2 Categorical retrieval columns

For an F1 categorical feature:

- Create the category vocabulary from the frozen training pool.
- Add an explicit unknown category.
- Use a non-ordinal encoding, such as frozen one-hot encoding, unless the categories have a documented ordinal meaning.
- Preserve the original category string for prompt display.
- Do not allow OOT categories to modify the vocabulary.

### 6.3 Excluded retrieval columns

Exclude:

- Fraud label.
- Account ID.
- Customer ID.
- Financial-institution transaction ID except as non-feature metadata.
- Any target outcome or post-transaction field.
- Raw transaction timestamp unless a pre-approved, point-in-time-safe transformation is used.

Reasons:

- Labels would create direct leakage.
- Identifiers can dominate similarity without representing transaction behavior.
- Raw timestamps can behave as arbitrary large numbers and can create time leakage.
- Metadata should remain available for joining, auditing, and parsing without entering the distance vector.

### 7.1 Source table

The source table follows the standard tabular convention:

~~~text
one row = one transaction
one column = one feature or metadata field
~~~

For a selected feature family with d features, a transaction row becomes an ordered feature vector:

~~~text
x_target = [feature_1, feature_2, ..., feature_d]
~~~

The order is determined only by the frozen feature manifest, never by incidental dataframe column order.

### 7.2 Candidate matrices

For F0:

~~~text
X_candidates_F0 shape = [number_of_training_candidates, 94]
x_target_F0 shape = [1, 94]
~~~

For F1:

~~~text
X_candidates_F1 shape = [number_of_training_candidates, d_F1]
x_target_F1 shape = [1, d_F1]
~~~

The current Spark candidate count may be approximately 77,884, but code must read the actual frozen manifest count.

### 7.3 Support matrices

After retrieval:

For DP_LOW:

~~~text
X_support shape = [2, d]
y_support shape = [2]
X_query shape = [1, d]
~~~

For DP_HIGH:

~~~text
X_support shape = [20, d]
y_support shape = [20]
X_query shape = [1, d]
~~~

This is already a tabular in-context-learning problem:

- X_support contains labeled example rows.
- y_support contains their fraud labels.
- X_query contains the unlabeled target row.
- Gemini receives a text serialization of this bundle.
- A tabular foundation model can receive the same logical bundle as native arrays/tensors.

### 7.4 Model-neutral ContextBundle

Build a model-neutral object before formatting:

  "support_ids": ["DEMO_1", "DEMO_2"],

  "y_support": [1, 0],
  "X_query": [[0.2, 1.7]],
  "retrieval_metadata": {
    "method": "D1",
    "policy": "DP_LOW_1F_1N"
  }
}
~~~

Do not send the model-neutral object itself to an external model unless its contents have passed the approved data-governance process. It is an internal contract that allows different adapters to consume identical experiment inputs.

### 7.5 Three distinct views

Maintain three explicit views:

1. X_retrieval
   - Imputed/encoded/standardized numeric matrix.
   - Used only to calculate D1/D2 rankings.

2. X_gemini
   - Human-readable or compact R0 values.
   - Uses safe, consistent feature names and display values.
   - Does not expose the target label.

3. X_tabfm
   - Native numeric/categorical arrays, masks, and column metadata.
   - Uses the same support/query IDs as the Gemini experiment.

These views may transform values differently for their consumers, but they must originate from the same feature-family manifest and the same frozen rows.

## 10. Frozen stratified development cohorts

### 10.1 Goal

The purpose of downsampling is to create a smaller development cohort whose label, segment, and time composition resembles the frozen OOT population closely enough for configuration screening.

No subset can be guaranteed to produce the exact same score as the full cohort before predictions are observed. Representativeness reduces risk; an empirical stability study measures the remaining risk.

### 10.2 Stratification variables

Use:

~~~text
fraud tag x segment x year-month
~~~

The actual columns may be named frd_tag and yyyymm. Record the exact column names in the manifest.

### 10.3 Required cohort sizes

Create nested frozen cohorts:

~~~text
OOT_DEV_200
OOT_DEV_400
OOT_DEV_600
OOT_FINAL_FULL
~~~

Required inclusion:

~~~text
OOT_DEV_200 is a subset of OOT_DEV_400
OOT_DEV_400 is a subset of OOT_DEV_600
OOT_DEV_600 is a subset of OOT_FINAL_FULL
~~~

The current 40-target cohort remains a smoke-test cohort only.

### 10.4 Use the full-cohort prevalence

Calculate the actual class distribution from the frozen OOT manifest first.

Do not assume the smoke split of 34 non-fraud / 6 fraud is the full-cohort prevalence. If the full cohort resembles the older 1,064 / 172 reference split, the fraud prevalence is approximately 13.9 percent and illustrative allocations would be:

| Total | Approximate non-fraud | Approximate fraud |
|---:|---:|---:|
| 200 | 172 | 28 |
| 400 | 344 | 56 |
| 600 | 517 | 83 |

These are examples only. Generate exact quotas from the current frozen manifest.

### 10.5 Exact quota algorithm

For each requested total n:

1. Count full-cohort rows N_h in every joint stratum h.
2. Calculate raw quota q_h = n times N_h / N_full.
3. Take the floor of every q_h.
4. Calculate the remaining unallocated rows.
5. Allocate remaining rows to the largest fractional remainders.
6. Break equal remainders using a deterministic stratum-key order.
7. Enforce nondecreasing quotas across 200, 400, and 600 so nesting cannot be violated.
8. If the number of nonempty strata is greater than n, do not force one row per stratum; preserve label totals first and report uncovered rare cells.

### 10.6 Deterministic Spark row order

Within each stratum:

1. Create a stable hash from transaction ID and seed 2026.
2. Sort by the hash.
3. Break hash ties by transaction ID.
4. Assign row_number within the stratum.
5. Take the first quota_h rows.

Do not use Spark sampleBy alone when an exact total and exact quota are required. Fractional sampling does not guarantee exact row counts.

### 10.7 Cohort validation

For each frozen cohort, save:

- Target IDs.
- Label.
- Segment.
- Year-month.
- Stratum key.
- Deterministic rank.
- Cohort membership flags.
- Seed.
- Source/full-cohort version.
- Creation timestamp.
- Manifest hash.

Validate:

- Exact requested total.
- Unique target IDs.
- No duplicate IDs.
- No IDs outside the full OOT manifest.
- Nested inclusion.
- Label proportions.
- Segment proportions.
- Year-month proportions.
- Joint-stratum counts.
- Null grouping keys.
- Numeric-feature balance against the full cohort.

Recommended balance diagnostics:

- Absolute categorical proportion differences.
- Standardized mean differences for important numeric features.
- Population Stability Index for approved binned summaries.
- Warnings for cells with fewer than five sampled rows.

Suggested development thresholds:

- Label allocation differs only by unavoidable integer rounding.
- Core marginal proportion differences are generally below two percentage points.
- Important numeric standardized mean differences are below 0.10.
- PSI below 0.10 where PSI is appropriate.

Threshold failures should be reported and diagnosed rather than hidden.

## 11. Empirical sample-size stability test

The phrase "very similar to the full score" must be converted into a prespecified tolerance.

Suggested initial tolerances:

~~~text
absolute ROC-AUC difference <= 0.03
absolute PR-AUC difference <= 0.03
absolute KS difference <= 0.03
~~~

These are project decisions, not universal statistical laws.

If at least one configuration has already been scored on every full-OOT target:

1. Keep its saved predictions fixed.
2. For n = 200, 400, and 600, draw 1,000 stratified subsets from the full predictions.
3. Recompute ROC-AUC, PR-AUC, and KS for each draw.
4. Compare every subset metric with that configuration's full-OOT metric.
5. Summarize median absolute difference, 90th percentile, and 95th percentile.
6. Select the smallest n whose 95th-percentile deviation satisfies the prespecified tolerance.

This simulation requires no additional Gemini calls because it uses already saved scores.

For stronger evidence, repeat the procedure using several diverse anchor configurations, such as one D0, one D1, and one D2 configuration. Use the stability evidence to choose cohort size, but do not choose specific transaction IDs because they happen to recreate one model's score. IDs must remain selected through the frozen stratification procedure.

## 13. Ranking and finalist-selection rules

Predeclare the selection rule before reading results.

Recommended rule:

1. Require complete or near-complete valid-score coverage.
2. Use ROC-AUC as the primary ranking metric.
3. Use PR-AUC as the first tie-breaker.
4. Use KS as the second tie-breaker.
5. Use lower initial failure rate as the third tie-breaker.
6. Use lower prompt tokens/latency as the fourth tie-breaker.

Do not rank a configuration with materially lower coverage as though it were directly comparable.

Use paired comparisons because every configuration receives the same targets. Where practical:

- Bootstrap targets, not individual predictions detached from targets.
- Calculate paired metric differences.
- Report confidence intervals.
- Treat configurations as tied when uncertainty intervals substantially overlap and the measured difference is operationally trivial.

Selecting the numerical maximum among many noisy configurations creates winner's-curse risk. The untouched final comparison is what turns the screen into a defensible conclusion.

## 16. Tabular foundation model bridge

The current work already implements the central structure used by many tabular foundation-model workflows:

~~~text
labeled support rows + unlabeled query row -> predicted query score
~~~

The difference is the input adapter:

### Gemini adapter

~~~text
ContextBundle
-> R0 row-to-text serialization
-> prompt
-> Gemini
-> JSON parser
-> fraud-risk score
~~~

### TabFM adapter

~~~text
ContextBundle
-> native X_support, y_support, X_query, feature names/types/masks
-> approved tabular foundation model
-> fraud probability/score
~~~

This permits an apples-to-apples benchmark:

- Same frozen training candidates.
- Same frozen OOT targets.
- Same F0/F1 feature definitions when compatible.
- Same support/query transaction IDs.
- Same metrics.
- Same cohort splits.

For a TabFM model that does not use a text prompt, P0-P3 should not multiply its grid. Its matched immediate grid is:

~~~text
2 feature sets x 3 support-selection methods x 2 support counts
= 12 TabFM configurations per approved model
~~~

Also evaluate a separate native TabFM baseline using the model's recommended full or larger training context when governance and compute allow. Do not conflate that native baseline with the matched small-support ICL comparison.

Do not automatically install, download, or transmit data to an unapproved tabular model. Record:

- Model license.

## 19. Presentation language

For the broad screen:

> Results from the 200-target cohort are development-screening evidence from a frozen stratified subset of the OOT population. Every configuration was evaluated on the same targets. The screen is used to advance configuration families and is not the final performance estimate.

For the stronger development comparison:

> Advancing configurations were evaluated on a nested 400-target frozen stratified cohort. These results provide stronger configuration-comparison evidence, while final claims are reserved for Y1 and Y2 on untouched OOT targets.

For the two-policy limitation:

> The immediate experiment compares two prespecified demonstration endpoints: 1 fraud plus 1 non-fraud versus 10 fraud plus 10 non-fraud. It measures the performance-cost difference between minimal and large context, but it does not establish the optimal intermediate demonstration count.

For the TabFM connection:

> Both the Gemini ICL workflow and a tabular foundation model consume the same logical object: labeled support rows, their labels, and an unlabeled query row. Gemini receives a text serialization of this object, while a TabFM receives native structured arrays or tensors.
