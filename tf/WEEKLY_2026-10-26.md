# Card-fraud transformer: seed check, final model, training setup and features

Week of 26 October 2026

## Summary

1. **Seed stability check: complete.** Arch B H20 chunk beat Arch B H20 sliding on all three seeds, by 0.0165 AP on average (about 20% higher), and it varies half as much from seed to seed.
2. **Final model: Arch B H20 chunk.** Its full specification is in section 2.
3. **Next: features, then scale.** Add 166 features: 90 TFM V22B fields, the 60 XGBoost-model features that TFM and our inputs do not already cover, and 16 we build ourselves. Redo preprocessing, retest on 10 training files, then train on 100 training files. Future results are reported on two test sets (section 3).

**The two models**

Both are architecture B (the reference setup's transformer) with a history of 20 (H20), and both are scored the same way: one window per transaction, ending at that transaction, the way a live system scores. Arch B H20 sliding's window is the transaction plus the account's 20 previous transactions. Arch B H20 chunk's window is the transaction plus the account's 20 previous time points (transactions in the same second count as one time point), at most 32 rows. They also differ in what each transaction can see and in how they are trained:

| Model | What it is | How it is trained |
|---|---|---|
| **Arch B H20 sliding** | The reference setup's best model. One fraud score per window. | Sliding windows: one window per transaction, one target per window. |
| **Arch B H20 chunk** | Architecture B with a fraud score for every transaction in the window, each computed from that transaction and earlier ones only. | Chunks: an account's history is cut into non-overlapping blocks of 21 time points, and every transaction in a block is a target. Within a block, each transaction sees only the earlier transactions of that block, so its history runs from 0 to 20 time points and restarts at each block. |

**Score used throughout:** average precision (AP), how well the model ranks frauds above legitimate transactions. A random score gets about 0.0015.

## 1. Seed stability check (complete)

**Question.** Training has random elements (starting weights, data order, dropout). Does the ranking hold when only the random seed changes?

**Design.**
- Both models retrained at seeds 43 and 44, next to the original seed 42: four new fits, one H200 GPU each.
- Everything else identical: same training set, same validation set, same recipe.
- All scored on Test 1 (section 3).

**Results (Test 1).**

| Seed | Arch B H20 chunk AP | Arch B H20 sliding AP | Difference | Arch B H20 chunk AUROC | Arch B H20 sliding AUROC |
|---|---:|---:|---:|---:|---:|
| 42 | 0.1020 | 0.0955 | +0.0065 | 0.9431 | 0.9520 |
| 43 | 0.0912 | 0.0743 | +0.0169 | 0.9462 | 0.9434 |
| 44 | 0.1013 | 0.0753 | +0.0261 | 0.9525 | 0.9439 |
| **Mean** | **0.0982** | **0.0817** | **+0.0165** | | |
| Spread across seeds (SD) | 0.0061 | 0.0120 | | | |

**What it shows.**
1. **The ranking held.** Arch B H20 chunk was ahead on AP on all three seeds, and its mean AP is about 20% higher. On AUROC it was ahead at seeds 43 and 44 and behind at seed 42 (0.9431 against 0.9520); AP is the deciding score because it measures the top of the ranking, where the alerts are.
2. **Arch B H20 chunk is the steadier model.** Its spread across seeds is half that of Arch B H20 sliding. Arch B H20 sliding's seed-42 score (0.0955) was the best of the reference setup's 15 variants on this same set, so part of it was the luck of being picked; at seeds 43 and 44 it came in about 0.02 lower.
3. **Seed noise is large.** One seed can move AP by up to about 0.02, which is why the decision rests on three seeds, not one.

**Second check: holdout set (evaluation files 8206-8216).** The same six fits were also scored on a holdout set of other accounts that was never used for training or for picking epochs; earlier rounds used it to compare model designs. Within each seed, both models were scored on exactly the same rows.

| Seed | Rows counted in AP | Arch B H20 chunk AP | Arch B H20 sliding AP | Difference |
|---|---|---:|---:|---:|
| 42 | June rows: 1,215,218 transactions, 2,081 frauds | 0.1103 | 0.0928 | +0.0175 |
| 43 | Full files: 2,504,003 transactions, 4,187 frauds | 0.1001 | 0.0666 | +0.0335 |
| 44 | Full files: 2,504,003 transactions, 4,187 frauds | 0.0995 | 0.0756 | +0.0239 |

Arch B H20 chunk is ahead at every seed on the holdout set too. (No mean is taken across seeds here, because the seed-42 AP counts June rows only and the seed-43 and seed-44 APs count the full files.)

## 2. Final model: Arch B H20 chunk

**Why this model.**
- It leads on every seed (section 1).
- Chunk training is what makes it win. The same model trained on sliding windows instead (same data, same number of training targets per epoch, same scoring) scores much lower:

| Arch B H20 chunk's model (history of 20 time points, seed 42), trained on | Test 1 AP |
|---|---:|
| Chunks (Arch B H20 chunk) | 0.1020 |
| Sliding windows (a separate seed-42 fit of this same model, not Arch B H20 sliding) | 0.0743 |

  The gap, +0.028 at seed 42, is well clear of test-set sampling noise: its 95% confidence range, from resampling whole accounts 1,000 times, is +0.017 to +0.038. Even Arch B H20 chunk's lowest seed (0.0912) is above the sliding-trained fit.
- It is scored exactly as production would score: one transaction at a time, using only that transaction and earlier ones.

**Specification.**

| Item | Setting |
|---|---|
| Architecture | Architecture B: a per-transaction encoder (2 transformer blocks) feeding a sequence encoder (4 transformer blocks); width 48, 8 attention heads, dropout 0.1 |
| Attention | Causal: each transaction sees only itself and transactions from earlier seconds; transactions that share a second do not see each other |
| History | At validation and scoring: the transactions from the 20 most recent earlier seconds in which the account transacted (all transactions in one second count as one time point), at most 32 rows per window including the target; a longer window keeps its 32 most recent rows (0.003% of Test 1 windows) |
| Inputs today | 23 fields (section 4), giving 30 input tokens per transaction: 7 numeric (the 6 numeric fields plus the time since the previous transaction) and 23 categorical (13 transaction codes, 4 calendar fields and 6 missing-value flags) |
| Training layout | Each account's history is cut into non-overlapping chunks of 21 time points; every transaction in a chunk is a target and sees only the earlier transactions of its own chunk (0 to 20 time points); all transactions used, none down-sampled |
| Loss | Cross-entropy, unweighted |
| Optimizer | AdamW, learning rate 0.0003, weight decay 0.00001; learning rate halved when validation loss has not improved for 4 epochs in a row |
| Epochs | Up to 10, stopping early after 5 epochs without a new best validation AP; validation is scored like the test sets (one window per transaction), and the epoch with the best validation AP is kept (the fourth epoch at seed 42) |
| Updates | About 4,100 training targets per update; 2,103 updates per epoch on training files 1-10 |
| Hardware | One H200 GPU; training and validation in bf16 mixed precision, test scoring in float32 |
| Scoring | One window per transaction, ending at that transaction; the score is the fraud probability at its last position |

## 3. Training setup

**Data.** Every file holds whole accounts: no account appears in more than one file, so training, validation and Test 1 never share an account. Training files 1-10 are part of training files 1-100. Test 2 is drawn from evaluation files 8000-8200, so 52,202 of its transactions are also in Test 1.

| Set | Files | Transactions | Frauds | Used for |
|---|---|---:|---:|---|
| Training (today) | training files 1-10 | 8,622,629 | 12,757 | Today's model and the feature retest |
| Training (scale-up) | training files 1-100 | 86,683,008 | 143,338 | The 100-file run |
| Validation | training files 4950-4954 | 4,292,059 | 7,285 | Picking the best epoch |
| Test 1 | evaluation files 8000-8010 | 2,466,461 | 3,818 | The main results so far, the final model choice, and every future test (May and June 2025) |
| Test 2 | the 952,905 transactions TFM V22B was evaluated on (from evaluation files 8000-8200) | 952,905 | counted at scoring | Head-to-head comparison with TFM V22B on the same transactions |
| Holdout | evaluation files 8206-8216 | 2,504,003 | 4,187 | The seed check's second reading (section 1) and feature selection (step 4 below) |

Training files cover October 2024 to May 2025.

**Test 2 in detail.** These are the exact transactions in TFM V22B's own evaluation file. TFM V22B scored AP 0.2737 and AUROC 0.9685 on them (its developer's results, reproduced in our rerun of the TFM model), with the status fields we leave out (section 4) among its inputs. Our model scores the same transactions from the raw evaluation files, with each account's earlier transactions as history, and the two are compared directly. AP depends on the fraud rate of the rows scored, so Test 2 numbers are compared only with TFM on the same rows, not with Test 1.

**Order of work.**

1. **Map the features to our data.** Check every proposed field (section 4) against the 224 columns of our files. Fields that are there are used directly. Fields that are not are built from the raw transactions where possible (time-window counts and amounts), or requested from the data owner (merchant claim rates, case outcomes).
2. **Redo preprocessing with the new features.** Category vocabularies and numeric scaling are fitted on training files 1-10 only, then applied unchanged to validation and test. Every history feature is computed only from data before the transaction.
3. **Retest.** Retrain Arch B H20 chunk with the new features on training files 1-10, with the same validation set. Score it on Test 1 (against today's model) and on Test 2 (against TFM V22B).
4. **Feature importance and selection.** Retrain with and without each feature group on training files 1-10, and keep a group only if it raises AP on the holdout set (evaluation files 8206-8216), with both fits read on the same accounts. Test 1 and Test 2 stay for reporting.
5. **Train on 100 files.** Training files 1-100, the same validation set and the same preprocessing, so the result differs from step 3 only by the amount of training data. Scored on Test 1 and Test 2 again.

Each transaction carries about 189 fields instead of 23, so the first retest epoch is timed before the 100-file run is scheduled.

## 4. Features

**What goes into the next model.**

| Source | Fields | How they go in |
|---|---:|---|
| Today's inputs | 23 | Kept as they are: 6 numeric (transaction amount, Visa's external score `external_1_scr`, and 4 balance and limit fields), 13 transaction codes, and 4 calendar fields (month, day of month, hour, day of week) |
| TFM V22B, the transaction foundation model | 90 new | TFM uses about 117 input fields. About 20 are already among our inputs and 7 status fields are left out (below); the other 90 are added. Full list: Appendix A |
| The bank's debit-card XGBoost model | 60 | Every one of the XGBoost model's features that TFM's fields and our inputs do not already cover. Full list: Appendix B |
| Built by us | 16 | Ratios, location jumps and longer count windows. Full list: Appendix C |
| **Total before selection** | **about 189** | |

**About the TFM count.** TFM's feature-importance chart has 120 rows, but they are not 120 fields: time appears as three tokens (time gap, hour, day of week) and one row appears to be a duplicate. That gives about 117 input fields. TFM's vocabulary of 5,378 is a count of tokens, not fields.

**The 60 from the XGBoost model, by group.** Each group is a set of similar features. The last column gives each feature's position in the XGBoost model's own importance ranking, where 1 is its most important feature.

| Feature group | Number of features | Their positions in the XGBoost model's importance ranking (1 = most important) |
|---|---:|---|
| 30-day merchant claim rates and counts | 9 | 3, 8, 16, 17, 24, 30, 34, 36, 69 |
| 14-day spending aggregates by card or customer | 15 | 39, 43, 62, 64, 66, 67, 71, 76, 79, 82, 84, 86, 87, 88, 90 |
| 24- and 48-hour velocity counts and recency | 10 | 7, 18, 25, 38, 42, 74, 80, 85, 89, 94 |
| Days since profile and history events | 11 | 5, 19, 26, 27, 50, 53, 61, 68, 75, 83, 91 |
| Recent account events (logins, mobile inquiries) | 3 | 41, 47, 58 |
| Merchant-name indexes | 3 | 35, 40, 60 |
| Account and card profile values | 9 | 15, 46, 51, 55, 59, 63, 70, 92, 93 |
| **Total** | **60** | |

The other 34 of the XGBoost model's 94 features are already in the set or left out: 25 are TFM fields we add (often the same raw field that the XGBoost model encodes), 7 are our inputs (positions 1, 14, 33 and 49 as they are, and positions 2, 4 and 12 as the XGBoost model's encoded versions of our codes), and 2 are status dates left out under the same rule as TFM's status fields (positions 22 and 78).

**How the features are treated.**
- **Only earlier data.** Every feature uses only data from before the transaction: count and amount windows end at the transaction, and profile values are taken as stored at the transaction time.
- **Codes go in raw.** XGBoost needs numbers, so the XGBoost model feeds codes such as MCC in as encoded numbers (its `derived_le1__` and `derived_le3__` features). The transformer does not need this. It learns its own 48-number vector for each code value, so it takes the raw field (for example `merchant_category_xcd`) instead of the XGBoost model's encoded version.
- **The bank's own decisions.** `FALCONDECLINE_INDICATOR`, `PREDECLINE_INDICATOR` and `PROCESSOR_REASON` record the bank's decision on the same transaction. As TFM does for `FALCONDECLINE_INDICATOR`, they are used for earlier transactions only.
- **Left out.** 7 status fields: `INACTV_DT` (card inactive date), the account status-change date, two online-banking login-block dates and three account and card status codes (listed in Appendix A). The TFM developer flagged V22B's status date as a fraud proxy, with leakage from the card inactive date. We apply the same rule to all seven: a status can change because of the fraud itself, so the stored value can reveal the outcome.
- **Claims.** Merchant claim rates use only claims known before the transaction.

## Appendix C: the 16 features we build

| Feature | What it captures |
|---|---|
| Amount ÷ available balance | Share of the balance this transaction uses |
| Amount ÷ remaining daily merchandise limit | Share of the remaining daily limit this transaction uses |
| Headroom code: overdraw, exact drain, 90% or more, 50-90%, under 50% | How close the transaction comes to emptying the account |
| Balance drained in the last 24 hours, this purchase included | A rapid cash-out |
| Transaction counts over 5 minutes, 1 hour, 24 hours, 7 days and 30 days (5 features) | Velocity beyond the model's 20-time-point window |
| MCC new for the account in the last 30 days | First use of a merchant type |
| Card-present transactions in the last 5 minutes, all entry methods (the XGBoost model's position 92 counts one transaction type only) | Bursts at a terminal |
| E-commerce transactions in the last 24 hours | Card-not-present bursts |
| Amount rank among the account's own amounts in the last 30 days | Unusual for this account |
| Distance from the previous located transaction | Location jump |
| Implied travel speed from the previous located transaction | Impossible travel |
| Distance from the home postal code | Away from home |

## Appendix D: exporting embeddings (after the 100-file model)

**What gets extracted.** For every transaction, the 48 numbers the model computes just before its fraud score: its summary of that transaction read together with the account's previous 20 time points (at most 32 rows). The fraud score is computed from these 48 numbers, so the vector holds everything the score uses.

- **Same pass as scoring.** The vector and the score come out of one forward pass, one transaction at a time. In production, scoring a transaction also produces its vector at no extra model cost.
- **No look-ahead.** Built only from the transaction and earlier ones. No label is read.
- **One model.** Taken from the final 100-file model only. Vectors from different models are never mixed.

**The export table: one row per transaction.**

| Column | Content |
|---|---|
| Transaction id, account id | Keys |
| Event time | When the transaction happened; the vector is valid from this time |
| Fraud score | The model's score for the transaction |
| History rows | How many transactions the window held |
| `e_0` to `e_47` | The 48 vector values |
| PCA 8 and PCA 16 | Compressed 8- and 16-number versions, fitted once on the downstream training accounts and then frozen |

**Checks on every export.** One row per transaction, no duplicate ids, every value finite, width 48, and the fraud score recomputed from the 48 numbers matches the model's own score to within 0.000001.

**Which accounts.** Only accounts the model never trained on: training files 4001-4010 to fit downstream models, evaluation files 8217-8227 to test them.

**Lookup.** For an account and a time T: the latest vector before T, and the account's average vector over the 30 days before T. Nothing at or after T is used.

**First two uses.**
1. **Transaction level.** XGBoost on raw fields + fraud score + vector, against raw fields + fraud score: does the vector add anything beyond the score?
2. **Account level.** XGBoost predicting a fraud on the account in the next 14 days, at weekly snapshots, from simple account history, with and without the latest vector.
