## Necessary corrections and independent disagreements

1. **R07: remove the invented universal0.01 AP threshold.** `bridge/audits/CL_review_phase4_v2_2026-10-06.md:38` says every documented gap is “far below anything one seed can resolve” and directs “decide nothing on a single-seed gap under0.01.” No data or uncertainty calculation establishes that threshold; single-seed result differences can be estimated conditionally on fixed trained models, while training-procedure variance remains unknown. Replace with: report observed gaps without claiming robust superiority/equivalence; estimate paired sampling uncertainty and repeated-seed variation; define a practical margin. Three-to-five seeds is an initial budget, not a universal power guarantee.

2. **R16 contradicts R01.** Audit:47 says the finder is “correctly described as a fresh rerun under the fixed code.” The current training imports demonstrably bypass the fix. The dry run verifies8 combinations and intended settings, not a correctly wired or executed clean rerun. Replace with “configured/intended fresh rerun; loader wiring and bank run provenance remain to be confirmed.”

3. **R12: h16 is optional, and h10 already has a historical A result.** Audit:43 calls h16 “the only long-history A result that exists,” but `my_work/docs/my_work_current_standing.md:46–47` records h10=.139942 and h16=.138256. Fresh A/B matching at h10/h15/h20 satisfies the updated grid; keeping h16 can help historical continuity but is not a methodological prerequisite. Existing stale h16 run_all comments should be updated, and resource constraints measured. “Prefer B for h20” is a cost hypothesis until actual throughput/quality are measured.

4. **R02: per-epoch file reshuffling is an optional optimization, not part of the correctness blocker.** Audit:33 correctly observes that the fixed shared seed preserves file order between epochs. The builder nevertheless partitions the full file list correctly; window shuffling remains active. Audit:52 should not require this extra change before a valid supervised run. Wiring the existing correct builder is the minimal repair. If the optional change is applied, record it as a changed sampling recipe and test reproducibility and worker lifecycle. EMA remains off for baseline controls; no optional EMA capability should block them.

5. **R05: record integrity deserves higher priority than hygiene.** Audit:36 classifies rerun overwrites/failed subprocesses as low. CH's independent actual-runner failure probes demonstrate an old AP0.9 returned beside train_rc=1 and then ranked as if relevant. That is a direct threat to experimental conclusions, not just a stale docstring. Immutable attempts, current-attempt-only metrics and failed-run exclusion should be prioritized before trusting new grid summaries. This does not mean every current unique run name collides: both reviews agree the15 scored rows of the six committed grids have distinct names.

6. **R08/Q8: distinguish later result families from contradictions.** Audit:39 and ASK:47–52 identify a real evidence gap, but “the same eight runs” is not established; the newer overview is explicitly a later chat record. The two dated tables can both be historically correct. If a new finder ran, older tables do not become false or need erasure; add a dated result family and provenance. The final AdamW decision means a newer optimizer winner does not automatically change every downstream setting. Ask for raw rows/config/code/artifact/cohort identity without presupposing table corruption.

The new single-seed observation is not yet established as an effect, and AdamW-only is an explicit downstream project choice. Keep AdamW as the replication baseline. ## Proposed h0 config assessment

The new config is a useful, correctly labeled proposal. Independent OmegaConf expansion produces exactly6 rows: h0/h5 × seeds42/43/44, AdamW, linear embedding, bidirectional attention, train1–10, validation4950–4954, batch4096, accumulation1, time_delta=true, `run_score=false`. It uses a separate output root; it does not run while merely stored under proposals. The execution comment names a not-yet-installed canonical `my_work/.../ft_decisions_h0_control.yaml`; for a review dry run use the actual proposal path or explain the proposed installation step.

Its comparison measures the benefit of the configured history extension in the same model family. It does not isolate every information source: h0 gives the target a zero time-gap, while h5 adds historical fields/time gaps; position-table/layout and initialization consumption differ. Pair it with the planned time-gap ablation, and optionally a fixed-slot masked-history control for stricter information-only attribution. Seeds42/43/44 can be paired as runs but do not force identical initialization for different parameter layouts. `run_score=false` appropriately avoids extra development-eval looks, but the existing runner exports no identified validation predictions; plan an explicit export to support paired statistical analysis of selected checkpoints.

The new h0 config does not address the independent h10 time-gap/capacity microbatch regression: those existing specs still inherit4096×1 instead of the known1024×4 setting. It also does not repair the runner lifecycle, analysis-utility errors, artifact provenance or bank timing/schema assumptions documented by CH. These are additions to the joint evidence, not reasons to reject the h0 proposal.
