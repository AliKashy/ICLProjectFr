## 1. Answers to the five questions

**1. Cheap proxies.** No to history 0, 1 or 5 as stand-ins. They are different models: a checkpoint trained at one history is refused at another, and window caps exist only for h20 and h5 (D:27-30). By slot counts h5 could cut an epoch by 1.7 to 2.8 times (derived, not timed), mostly in validation, and the saving shrinks once validation is made faster (D:22). Chunk training reads each row about once per epoch at any history (D:21; A:60). Sliding training re-reads the history for every target (A:61). Target-ending validation re-reads up to 32 rows per target, an estimated 76-84% of a chunk-h20 epoch by FLOP count (derived, not timed; D:40). The real problem: no run shows that a short-history ranking matches h20 (D:32-33). Trusting one would take four settings at both fidelities, eight fits (A:72). It is not worth it here. What saves time and keeps the model: fewer epochs (your 4 or 5 epoch drop rule), a faster validation pass after a match test (D:42-45), and two trials at once if the GPU is under-used (CL2 #20). Fewer files change the data mix and leave validation cost as it is (A:44); a smaller validation set makes AP noisier (A:45). `train_stride` does not work for chunks (D:49). To check the drop rule itself, the search's first 8 trials run to 10 epochs with the drop decision logged, so we can count settings it would have cut that later caught up. Tonight's runs check the order among kept runs only.

**2. Tuning the chosen model.** We tune only the chosen model, as you decided: h20, chunk training, files 1-10, full epoch validation; only epochs are cut. Main search (stage 2): AdamW learning rate 5e-5 to 1e-3, moved if tonight's best rate sits at an edge; weight decay 1e-6 to 0.5, with a switch for no decay on embeddings, norms and biases; attention and feed-forward dropout 0 to 0.5; gradient clipping off or at 1.0. Thirty trials. A trial stops after 5 epochs if it is more than 0.03 below the median of the three best 5-epoch scores so far; otherwise it runs to 10. The best four and today's settings race on three new seeds, and the leader is confirmed on three more. Depth (1-3 transaction blocks, 2/4/6 sequence blocks) and heads (4 or 8) are tuned after the features, on the about 190 tokens per transaction they depend on (CL2 #4). Width 48 and history 20 stay fixed. Sequence depth and heads interact with history (D:113), so none is screened at a shorter history; dropout needs full-length runs (D:114), so survivors run to 10 epochs. Budget: section 4 gives each stage's maximum in epochs. Before stage 2 you get the stage 2-4 maxima in GPU-days from stage 1's timings, and you decide whether to trim.

**3. Feature screening.** On the h20 model, not a short-history one. A short-history model overrates features that stand in for the missing history, such as velocity counts and days-since fields. It underrates features whose value shows only with long context (A:140). CPU checks come first: availability at scoring time, missing values, duplicates, and rolling features built from the full earlier history (A:136). V32B goes into the base, as you said (Q:2734), and stays unless clearly worse. The 15298 features are picked from 15298's importance list (Q:503) and tested as one group. Month is out and the time gap stays (Q:249-252). Tokens per transaction rise from about 30 to about 189-194 (D:101), so their cost is timed in stage 1, before any budget is set (CL2 #4).

**4. Recipe options and the production model.** Yes to some, each with its own control and a rule set in advance (section 2). Code for EMA, schedules and decay groups, PLR, the loss options, the tuner and the CPU checks is being built, off by default (Q:128-135). SOAP, Muon routing, the clipping switch, the monitor fix, update-based validation and the downstream scripts need new code later. Three seeds resolve only about 0.022 AP (T_3 at sd_pair 0.008; D:76-79 gives about 0.021 without the account term), and most published gains for these methods are smaller, so each needs a clean test. The production model is one frozen checkpoint, trained on files 1-100 without month. Its score and its 48 numbers come from the same pass (`waqas/v2/export_v2.py`@60232e9:137-150). Then calibrate if a probability is needed, freeze everything and read FINAL once.

**5. Order of work.** The earlier order was sound. Comparing architectures under one recipe is a normal way to narrow the field; the claim is "best under this recipe", not "best once tuned" (A:182). Every earlier gap could move under tuning: chunk over sliding +0.0277 (one seed), chosen over reference +0.0165 (three seeds), the h15/h20 tie, and h5 worst (A:184-189). Tonight's light check tests each contender's learning rate. A change of model needs a common-seed comparison (stage 0b; R:88-90; A:90). Chunk against sliding is not re-opened unless a decision needs it (A:94). Practitioners usually fix the inputs, then tune, then scale. We follow your order (reproduce, tune, features, 100 files, embedding) with two checks added: a re-tune on the final inputs, and a learning-rate and regularization re-check at 100 files (D:103; CL2 #4, #15).

## 4. The plan, stage by stage

**Decision rules, written into the decisions file before the read they govern** (formulas in the note at the end).
- Free settings (learning rate, decay, the decay-groups switch, dropout, clipping): the leader is adopted if its mean over fresh fits on RANK-B is higher than the incumbent's and it passes the SELECT check.
- Changes that add code, cost or risk (EMA, schedule, loss, PLR, more blocks or heads, the 15298 group, SOAP, Muon): the mean paired gain on RANK-B over n fresh fits must beat a noise bar, T_n, and pass the SELECT check. At the planning figures T_3 is about 0.022 and T_2 about 0.025 (CL2 #6). With the chosen model's own seed spread it could be nearer 0.014 (estimate).
- Noise: the seed spread comes from the race's RANK-A scores (5 settings, 3 seeds each), used whether it is above or below the old 0.013; until then, from the seed 42/43/44 validation curves (CPU item 5). The account noise comes from each comparison's own bootstrap (D:76-79).
- SELECT check: one logged read. The paired difference must not fall below minus one SE of that difference, for AP, AUROC, KS and UDR at 0.6% (CL2 #7, #19). CPU item 1 measures the typical SE now (about 0.008 to 0.010 AP, estimate from P2:228), and the decisions file states the observed gain each check needs. The 90% interval is reported.
- Fits that chose a winner never decide it, and fits that led to an adoption are never a later control: each later control is a fresh refit (CL2 #6). If a result is unresolved, keep the simpler or cheaper option (A:152).
- Screening (the drop rule and the search's objective) stays on AP. If you pick VDR or UDR as the main metric, its seed spread and SE come from CPU and its bar is set before stage 0b.
